# Canonical dependency provenance

Inspected on 2026-09-06 at exact base `eb7a7650a3541d08630ed60d4e684f495123d343`; source drift against the base was empty. Before implementation, the legacyBackend.ts file SHA256 was `155fc772638916af07615fe8b269afda2e8e6f444aa7610009714cfe0ed5d1f5` (Windows checkout bytes).

- Both callers normalize the request entry with `normalizeBoundaryPath`. This strips query/hash suffixes and resolves existing aliases or the closest existing parent for missing paths. The collector's `path.resolve(entryFileName)` therefore preserves that canonical identity.
- `projectTrackedFiles` has only two population paths: initial project membership and Program-derived membership. Both go through `syncFiles`, which invokes `normalizeBoundaryPaths` before inserting paths. Configuration parsing, referenced projects and compiler source names remain real normalization boundaries; none is changed.
- Direct dependencies start as raw compiler/module/type-reference paths. `collectDirectTrackedFileDependencies` retains only exact strings already present in `projectTrackedFiles`. Its cached edges are consequently canonical. Shared ambient paths have the same exact-membership filter before becoming traversal seeds.
- The collector adds only its normalized entry, the filtered ambient seeds and those filtered direct edges. A new Set owns the traversal result, deduplicates diamonds/cycles and returns a fresh sorted array. No mutable cached edge array is returned to a caller.
- Dependency caches belong to a Program through a WeakMap. Changes clear that map; delete/create/config changes reset or rebuild project state. Initial creation, reset and disposal clear membership/cache state. Program synchronization refreshes membership on an active Program change; switching referenced ProjectService Programs already has focused coverage in backendParity.test.ts.
- The success and validation paths synchronize the active Program before collecting. A parser callback can throw before that synchronization; the error path still collects only the normalized entry and previously canonical membership. The optimization does not change error-path membership, graph reachability or synchronization timing.
- `prepareCacheValidation` still waits for pending watch changes and checks the lifecycle, latest revision and active source-file presence. The patch will not change these guards, unresolved-candidate normalization, update boundaries, config normalization or watch registration.

The new test file passed on unchanged production code: four cases across `legacy` and `project-service`. It uses a real junction on Windows / directory symlink elsewhere for component requests and update paths, including query/hash suffixes. A transitive diamond, unrelated component and selected ambient declaration assert exact physical dependency arrays. Each edit, delete, recreation and config path/ambient switch compares full metadata and dependencies with a fresh backend. Older arrays remain unchanged, stale validation revisions are rejected, and controlled parser errors before first successful extraction and after a reset agree with validation and recovery. See `baseline-canonical-tests.txt`.

The canonical assertion uses the filesystem's physical fixture root plus explicit expected filenames; it does not invoke the production normalization helper or infer expected graph membership from actual output. The tests do not assess live alias retargeting without a corresponding backend update/reset.

Existing test coverage was inspected before adding cases: referenced-project/ambient switching and cyclic transform orders in backendParity.test.ts; real alias resolution and missing-file watch rejection in backendContract.test.ts; persisted missing-alias identity and selective HMR in persistentCacheFreshness.test.ts. The focused/full-suite gates retain these cases unchanged.

Conclusion: the three final whole-array normalization passes are redundant for the backend-owned collector output under the existing lifecycle. Remove only those passes, retaining the actual producer/input normalization boundaries.
