# Implementation Plans

Generated by the `improve` skill after a deep repository audit and triage of
every open issue, then revised on 2026-07-20 around a hybrid legacy/native
roadmap. All plans are stamped against commit `ffd553b`; later plans explicitly
expect the earlier dependency plans to have changed their in-scope files.

The strategic decision is intentionally conservative: fix the current package
boundary and known correctness/security problems, then extract a high-level
backend seam, test an exact-pinned native implementation privately, and keep the
legacy backend until a separate production gate is passed. Do not replace the
whole roadmap with a flag-day rewrite, and do not publish an unstable backend
from the feasibility spike.

After the native spike recorded `CONDITIONAL`, Plan 009 adds a narrower
TypeScript 6 decision gate. It compares the shipped ProjectService-backed
LanguageService path with the private direct extractor before authorizing
either promotion work or a parser rewrite.

Plan 010 closes the remaining shipped-runtime gap by comparing WatchProgram
with ProjectService under the same controlled Vite/HMR evidence. Only a
confirmed ProjectService result proceeds to a stable opt-in, deprecation of
the two experimental booleans, and a packed TypeScript 4.3–6 / Vite 3–8
compatibility matrix. The default switch and WatchProgram removal remain a
later release gate.

Plans 011–015 close the release-readiness findings selected after Plan 010:
commit-exact pinned publishing, dependency-safe cold cache reuse, an explicit
Node/runtime dependency contract, complete packed coverage for every shipped
runtime, and dynamic project membership without restart. Only after those
correctness and release gates land may Plan 016 measure cached project-state
snapshots and indexed membership. Neutral evidence does not authorize keeping
that optimization.

Each executor must read its plan fully, honor every STOP condition, run every
verification gate, and update only its status row here when done.

## Recommended execution waves

### Wave 1: stabilize the current product

- Plans 001, 002, 003, and 004 are logically independent and may use separate
  branches.
- Plans 001 and 002 both intentionally touch root `package.json` and
  `yarn.lock`. Whichever merges second must rebase, preserve both `yaml` and the
  TypeScript aliases, run `yarn install`, and commit the regenerated combined
  lockfile. Never resolve that conflict by taking one side wholesale.
- Plans 002 and 004 are independent in behavior but both edit `README.md` and
  `src/index.ts`; do not implement them concurrently in one worktree. Whichever
  merges second must rebase, preserve both the compatibility loader/diagnostic
  and the selection/no-load boundary, then run both focused suites plus
  `index.test.ts`, typecheck, and build before Plan 005 freezes its ledger.
- Plan 003 is the smallest correctness fix and provides the target grammar that
  Plan 006 later makes compiler-neutral.
- Plan 004 owns selection/project membership. It must land before the HMR
  fixture so a referenced component cannot be rejected before HMR runs.

### Wave 2: turn the reported HMR behavior into a gate

- After Plans 002 and 004 land, Plan 005 adds a real Vite watcher/module-graph
  contract with an exact legacy failure ledger across two topologies and four
  legacy modes. Its first real-server run also applies the narrowly proven
  pre-transform ordering needed to keep project-service input typed; that
  prerequisite receives a patch changeset but does not claim issue #57 is
  fixed. Freezing after both prerequisites prevents a compiler or selection
  rebase from silently changing the characterized baseline.
- Known failures are recorded as named observations, not skipped tests or
  `it.fails`; unexpected failures and unexpected passes both require review.

### Wave 3: create the hybrid seam

- Plan 006 extracts a high-level backend session. The host retains Vite hooks,
  caches, dependency reverse indexes, generation, and invalidation; the backend
  owns compiler/project lifecycle, extraction, targets, dependency discovery,
  freshness, and disposal.
- `react-docgen-typescript` remains intact inside the legacy backend. The plan
  neither copies its source nor wraps native objects in a legacy compatibility
  facade.
- All existing transform snapshots and Plan 005 observations must remain
  unchanged. A behavior fix during extraction is a STOP condition, not a bonus.

### Wave 4: evaluate native, then deliver the current-backend fix

- TypeScript 7 is now stable, but 7.0 still has no stable programmatic API.
  Plan 007 uses Plan 002's exact `typescript@7.0.2` alias plus an exact
  7.1-next churn probe, imports only declared high-level unstable subpaths, and
  builds the prototype under a private non-workspace experiment directory. A
  direct TypeScript 6 LanguageService extractor is retained in that experiment
  as a control arm so extraction/session improvements are measured separately
  from native-compiler improvements. It
  cannot alter the published manifest, build entry, peer range, exports, README
  support claims, or release notes.
- The spike must prove in-memory Vite source, project references, canonical
  metadata, exact dependency paths, two-edit selective HMR, clean teardown, and
  same-machine performance and the actual packed artifact. Before attributing
  an HMR failure to native, a known-fresh fake backend must pass the unchanged
  real-Vite runner; a shared host failure blocks the spike and routes to Plan
  008's host branch. Missing native stable core support or reliance on the
  declared low-level protocol/private internal surfaces is a NO-GO, not
  permission to improvise.
- The parity evidence has two ledgers. The public-contract ledger remains exact
  for DTO shape, options, targets, dependencies, ordering, and supported legacy
  behavior. A separate quality ledger records reviewed intentional differences
  for false-positive functions, polymorphic components, HOCs, compound/member
  components, namespace imports, and discriminated unions. Pin representative
  real-design-system fixtures or source patterns from Flowbite, Reshaped, Park
  UI, Primer, and Mantine rather than treating legacy defects as required
  compatibility.
- Plan 008 preserves the earlier detailed issue #57 investigation behind the
  new seam. Plan 005 supplies deterministic symptoms; Plan 008 first isolates
  backend freshness/dependencies from host cache/index/delivery, then removes
  every ledger entry using only the causally proven branch. This work is not
  optional while legacy remains available to users.
- A later native default switch requires full public-option parity,
  compatibility CI, packaging review, rollback evidence, and an explicit
  repair-or-removal decision for legacy.

### Wave 5: select the competitive TypeScript 6 production path

- Plan 009 compares four controlled arms: default legacy, shipped
  ProjectService plus the upstream parser, and the private direct
  LanguageService extractor with its DocumentRegistry on and off.
- The product decision uses end-to-end Vite cache and two-edit HMR timing. The
  earlier native benchmark's direct-backend warm calls are not substituted for
  a real warm transform.
- If the existing project-service path provides the material gain, promote it
  in a separate rollout plan and avoid a parser rewrite. If direct extraction
  provides an additional material gain, write a separate full-parity plan
  around per-tsconfig LanguageServices and a manager-scoped registry; the
  experiment control is not shippable verbatim. If neither wins, retain the
  current default.
- Plan 009 changes no public option, default, manifest, peer range, production
  source, changeset, or package artifact.

### Wave 6: confirm the shipped runtime and begin convergence

- Plan 010 first adds WatchProgram to the independent paired evidence. Plan
  009 rejected a direct parser rewrite, but it did not prove ProjectService is
  preferable to every already-shipped runtime.
- A material WatchProgram advantage or an ambiguous result stops the rollout.
  Valid neutral evidence favors ProjectService only when it remains within the
  authored cold/HMR and memory budgets, because ProjectService consumes Vite's
  in-memory source without a second filesystem-watcher lifecycle.
- On `PROJECT_SERVICE_CONFIRMED`, add a stable
  `docgenMode: "legacy" | "project-service"` selector while keeping the
  current legacy default. Both experimental booleans remain compatible for a
  deprecation window but warn once and cannot be mixed with the stable option.
- Validate the actual packed plugin across pinned representatives of
  TypeScript 4.3–6 and Vite 3–8. Do not shrink the peer ranges or silently
  fall back by compiler version to make ProjectService appear stable.
- A later next-major plan may make ProjectService default and remove
  WatchProgram only after at least one stable-opt-in release remains clean.
  TypeScript 7 stays research-only until its programmatic project/checker API
  removes the measured request amplification and reruns the same gates.

### Wave 7: make the stable opt-in release-ready

- Plan 011 makes production publishing depend on the same commit's full
  verification and pins privileged workflow actions.
- Plan 012 closes the known cold-cache freshness gap before the cache can be
  promoted beyond an opt-in.
- Plan 013 makes the already effective Node floor explicit and removes the
  vulnerable direct glob/minimatch path without changing peer families.
- Plan 014 extends the packed matrix from one runtime to the complete shipped
  contract, adds focused Windows coverage, and reuses one commit-bound archive.
- Plan 015 handles matching TypeScript files created, deleted, or recreated
  after initialization without adding a second watcher lifecycle.

### Wave 8: optimize only from attributed evidence

- Plan 016 compared the unchanged final baseline with cached immutable
  project-state snapshots and host-side membership indexes using ten
  alternating independent direct-plugin timing pairs, while unchanged
  real-Vite contracts remained the correctness gate.
- The final variance remained inconclusive and the candidate missed the
  cold-transform keep threshold while several timing rows regressed. The
  optimization was not integrated; Plan 015 remains the production source.

## Native decision gate

Plan 007 first records `BLOCKED` with no verdict if oracle drift, a failing
known-fresh host preflight, infrastructure, invalid benchmark evidence, or
unusable timing prevents a native-specific conclusion. Once those controls are
valid, it records one verdict in `docs/native-backend-spike.md`:

- **NO-GO** is evaluated first: stable 7.0.2 fails a hard source/reference/
  dependency/metadata/HMR/teardown gate, needs low-level/internal wire access,
  or has a confirmed greater-than-50% large regression with no supported route.
- **CONDITIONAL** is next: stable correctness passes but the exact next probe,
  wider parity/order/callback contract, or performance gate remains unresolved;
  this includes every confirmed 16–50% regression and neutral results. Keep
  legacy default, name the exact retry gate, and execute Plan 008.
- **GO** applies only after those disqualifiers are absent: stable and next hard
  gates plus wider parity/order pass, every large metric regresses at most 15%,
  and the same winning metric (cold or imported edit) improves at least 20% on
  both large fixtures in confirmation samples. Write a new production plan; do
  not ship from the spike.

All three verdicts retain the Plan 008 obligation while legacy is supported.

The decision record must also report three-arm attribution: current
`react-docgen-typescript` adapter → direct TypeScript 6 LanguageService control
measures extractor/session design, while that control → direct TypeScript 7
native measures compiler/API effects. Storybook benchmark numbers are
directional context only; they are not substituted for the plan's paired local
evidence.

## Cross-plan ownership rules

- `src/utils/fileSelection.ts` owns include/exclude semantics. Backends receive
  its result; they do not reinterpret globs.
- The Plan 006 host owns Vite filtering/hooks, transform caches, reverse
  dependencies, generation, warnings, affected-node return/delivery, and the
  contract under which Vite core performs module-graph invalidation.
- A backend owns compiler loading, config/project state, extraction, targets,
  dependency discovery, update readiness, reset, and disposal.
- The compiler-neutral DTO/target grammar may not contain TypeScript, native,
  Vite, or upstream parser objects.
- Plan 007 owns only its private experiment files/tests/benchmark/evidence. Plan 008
  owns only the legacy release fix. Neither may weaken the other backend's
  contract or test ledger.

## Findings and approaches considered but rejected

- **Replace the issue roadmap with a rewrite**: rejected. Security, compatibility
  truthfulness, target safety, and selection bugs are independent of parser
  architecture and should not wait on unstable compiler research.
- **Copy/in-line `react-docgen-typescript` into the current plugin**: rejected.
  It increases maintenance immediately while preserving the same legacy API
  coupling. Plan 006 isolates it as a legacy adapter; Plan 007 writes only the
  native vertical slice against a local DTO.
- **Adopt Storybook's first virtual-probe design as the production
  architecture**: rejected. Storybook's closed
  [#33909](https://github.com/storybookjs/storybook/pull/33909) was superseded
  by merged
  [#33914](https://github.com/storybookjs/storybook/pull/33914), which removed
  synthetic probes because they invalidated compiler caches and instead used
  JSX already present in story files. This plugin has no equivalent story
  context, so Plan 007 may measure stable-content batched probes only as an
  experiment and must record their snapshot/cache churn.
- **Expose a TypeScript `DocumentRegistry` through the neutral backend
  contract**: rejected. Storybook
  [#35468](https://github.com/storybookjs/storybook/pull/35468) is useful
  evidence for sharing parsed sources across compatible per-tsconfig legacy
  LanguageServices, but the registry is a legacy compiler implementation
  detail. Plan 007 measures it on/off in the TypeScript 6 control when that
  architecture applies; Plan 006 expresses only shared session ownership.
- **Shim native objects into legacy Program/Checker/Symbol shapes**: rejected.
  The surface is too broad, would be brittle across unstable API revisions, and could
  erase performance gains through chatty synchronous IPC.
- **Claim TypeScript 7 support because unstable subpaths exist**: rejected.
  Stable TypeScript 7.0 explicitly ships no stable programmatic API, and its
  root is not the legacy compiler contract this package needs. Plan 002
  advertises the truthful production boundary; Plan 007 is non-shipping.
- **Silently drop RegExp entries before glob discovery**: rejected. It would
  make project membership and transform filtering disagree. Plan 004 rejects
  invalid runtime input.
- **Treat every referenced-project source as eligible regardless of patterns**:
  rejected. Project membership and plugin selection are separate boundaries;
  both must accept a file.
- **Synthesize imports for barrel re-exports**: rejected for the bug fix. It
  changes module execution/tree-shaking semantics. Plan 003 skips a target with
  no local binding.
- **Fix #57 by invalidating every transformed component on every `.ts` edit**:
  rejected. It masks dependency bugs and scales poorly. Plans 005/008 preserve
  a selective reverse dependency index.
- **Use `it.fails`, skip, or todo for #57**: rejected. Fixture/setup failures
  could satisfy an expected failure. Plan 005 uses exact semantic ledgers with
  hard infrastructure assertions.
- **Add Storybook or Nx to the first HMR gate**: rejected. Start with Vite's
  public server/module graph; STOP and seek separate authorization if that
  cannot reproduce stale metadata faithfully.
- **Keep snapshot build and publish on one runner while narrowing the token to
  one step**: rejected. Pull-request code can leave a background process. Plan
  001 requires a fresh privileged runner and treats artifacts as hostile data.
